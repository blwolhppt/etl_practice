# Жизненный цикл ETL-задачи

## О проекте

Разработайте на Python отказоустойчивый ETL-пайплайн: от проверки входных файлов до транзакционной загрузки данных в базу. Пайплайн должен отслеживать состояние задачи, вести журнал событий и автоматически освобождать ресурсы после завершения работы или ошибки.

**Ориентировочное время:** 10–12 часов, включая разработку, тестирование, настройку, отчёт и демонстрационное видео.

## Цель

Научиться организовывать полный жизненный цикл обработки данных: извлечение из архива, валидацию, преобразование, загрузку, обработку ошибок и очистку временных ресурсов.

## Сценарий

Пользователь запускает программу, передавая путь к ZIP-архиву с CSV-файлом. Программа проверяет архив и данные, преобразует записи и сохраняет результат в базу данных. Повторный запуск с теми же данными не должен создавать дубликаты.

Для учебного проекта достаточно локального запуска и SQLite. Можно выбрать другую реляционную СУБД, если инструкция позволяет воспроизвести решение.

## Входные данные

Архив должен содержать один файл `orders.csv` в кодировке UTF-8 с разделителем `,` и заголовком:

```csv
order_id,customer_id,order_date,amount
1,101,2026-01-15,1500.50
2,102,2026-01-16,750.00
```

| Поле | Требования |
| --- | --- |
| `order_id` | Положительное целое число, уникальный идентификатор заказа |
| `customer_id` | Положительное целое число |
| `order_date` | Существующая дата в формате `YYYY-MM-DD` |
| `amount` | Неотрицательная денежная сумма, не более двух знаков после точки |

Дополнительные столбцы можно игнорировать. Пустой файл, отсутствие обязательных столбцов, неверные значения и повторение `order_id` внутри файла считаются ошибками. При любой ошибке валидации весь файл отклоняется; частичная загрузка не допускается.

## Функциональные требования

### 1. Запуск и конфигурация

- Реализуйте запуск из командной строки с указанием пути к архиву и базы данных.
- Пример интерфейса: `python -m etl --archive data/orders.zip --db data/orders.db`.
- Предусмотрите понятное сообщение об успешном завершении или причине ошибки.
- Возвращайте код завершения `0` при успехе и ненулевой код при ошибке.

### 2. Извлечение и валидация

- Проверьте, что входной путь существует и указывает на корректный ZIP-архив.
- Проверьте наличие ровно одного `orders.csv` в корне архива.
- Используйте отдельную временную директорию для каждого запуска.
- Не допускайте извлечения файлов за пределы временной директории, в том числе через пути с `..` или абсолютные пути. Можно читать только ожидаемый файл, не распаковывая архив целиком.
- Проверьте структуру CSV и все записи по правилам выше.
- При ошибке укажите причину, а для некорректной записи — номер строки и поле.

### 3. Преобразование

- Удалите пробелы по краям значений.
- Приведите идентификаторы, даты и суммы к соответствующим типам.
- Для работы с денежными значениями используйте `Decimal`, а в базе храните сумму в целых копейках в поле `amount_kopecks`.
- Добавьте поле `order_month` в формате `YYYY-MM`.

### 4. Транзакционная загрузка и идемпотентность

- Создайте таблицу `orders` с полями `order_id`, `customer_id`, `order_date`, `amount_kopecks`, `order_month`. Поле `order_id` должно иметь ограничение уникальности или быть первичным ключом.
- Выполняйте загрузку всего файла в одной транзакции: либо сохраняются все изменения, либо ни одно.
- Если заказ уже существует, обновляйте его данные по `order_id` — используйте семантику upsert.
- Повторная обработка одинакового файла должна оставлять содержимое таблицы `orders` неизменным.
- Если для существующего `order_id` пришли новые значения, после успешного запуска в базе должны находиться новые значения.

### 5. Статусы задачи

Для каждого запуска создавайте отдельный `run_id` и сохраняйте состояние в таблице `etl_runs`.

Успешный запуск проходит состояния:

```text
PENDING → EXTRACTING → VALIDATING → TRANSFORMING → LOADING → SUCCESS
```

При ошибке после регистрации запуска устанавливайте `FAILED`. Храните как минимум:

- идентификатор запуска и путь к исходному архиву;
- текущий статус;
- время начала и завершения;
- количество обработанных записей при успехе;
- описание ошибки при неуспешном завершении.

Статус `SUCCESS` устанавливайте только после фиксации данных. Запись об ошибке должна сохраняться после отката транзакции загрузки. Если база недоступна и сохранить статус невозможно, сообщите об этом через журнал и ненулевой код завершения.

### 6. Логирование и очистка

- Ведите журнал с временем события, уровнем, `run_id` и сообщением.
- Логируйте начало и завершение этапов, итог обработки и ошибки. Для неожиданных ошибок сохраняйте traceback.
- Закрывайте файлы и соединения с базой и удаляйте временную директорию как при успехе, так и при обрабатываемой ошибке.
- Исходный архив не изменяйте и не удаляйте.
- Автоматическое восстановление после аварийного завершения процесса, отключения питания или `kill -9` в обязательную часть не входит.

## Требования к реализации

- Используйте Python 3.11 или новее.
- Разделите извлечение, проверку, преобразование, загрузку и управление запуском на отдельные функции или модули.
- Не храните пароли и другие секреты в репозитории.
- Зафиксируйте зависимости и опишите установку.
- Веб-интерфейс, Docker, оркестратор задач и параллельная обработка не требуются.

## Проверка решения

Добавьте автоматические тесты для следующих сценариев:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Корректный архив | Все записи загружены, преобразования выполнены, статус `SUCCESS` |
| Повторный запуск того же архива | Дубликатов нет, данные заказов не изменились |
| Изменённые данные существующего заказа | Заказ обновлён, дубликат не создан |
| Файл отсутствует, архив повреждён или нет `orders.csv` | Понятная ошибка, статус `FAILED`, данные заказов не изменены |
| Отсутствует обязательный столбец или есть неверное значение | Файл отклонён целиком, статус `FAILED` |
| Повторяется `order_id` внутри CSV | Файл отклонён целиком |
| Ошибка после начала записи в базу | Все изменения текущей загрузки отменены, статус `FAILED` сохранён |
| Успех или обрабатываемая ошибка | Временные файлы удалены, ресурсы закрыты |

В тесте отката искусственно вызовите ошибку после записи хотя бы одной строки, но до фиксации транзакции. Проверьте, что состояние таблицы `orders` совпадает с состоянием до запуска.
